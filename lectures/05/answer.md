第５回宿題「実装」

１ 実験事項
　app/retrieval.py の search() を改良し、ベクトル検索でヒットした各ページと同じ document_id に属する前後1ページ（page - 1とpage + 1）を load_pages(RAG_SOURCE) から取得して追加するように変更し、存在しないページのスキップと page_id による重複除外を実装した。
　変更前後で 「uv run python -m app.retrieval」および「uv run python -m app.agent --trace」を実行して比較した。
　使用モデルはgemini-3.5-flash-liteとした。

２ 結果
(1) 質問
「"第3回の例では、コンパクションとセッションをまたぐメモリはどう違いますか。日々のメモはすべて長期メモリに入りますか"」

(2) 変更前後の情況
＜変更前（通常検索）＞
取得ページ数：5ページ（p.65, 39, 38, 40, 13）
回答・引用根拠：コンパクションとメモリの違い、日々のメモの選別を説明（p.39, 40, 65）
入力トークン数：2,500 tokens
出力トークン数：472 tokens
応答時間[time]：7.20 秒
推定コスト[cost]：$0.001930 USD

＜変更後（前後1ページ追加）＞
取得ページ数：11ページ（p.64, 65, 66, 38, 39, 40, 37, 41, 12, 13, 14）
回答・引用根拠：コンパクションとメモリの違い、日々のメモの選別を説明（p.39, 40, 65）
追加された情報（ノイズ・周辺）：p.64（長時間タスク）、p.66（AGENTS.md/Skills）、p.37（章扉）、p.41（Skill）、p.12（ループ）、p.14（モデル＋ハーネス）
入力トークン数：4,596 tokens
出力トークン数：405 tokens
応答時間[time]：7.16 秒
推定コスト[cost]：$0.002391 USD

(3) 変更前後の変化
 • 重複を除外しつつ、ヒットページの前後1ページが追加された。
 • 今回の質問では回答内容自体は大きく変化しなかった。 
 • 質問と直接関係しない周辺ページも混入した。
 • 入力トークン数は +2,096 tokens（約1.84倍）増加した。
 • 出力トークン数は -67 tokens 減少した。
 • 応答時間はほぼ同等であった。なお、たびたびモデルの混雑による503エラーが
　出ており、応答時間は混雑状況の影響を受けていると考えられる。
 • 推定コストは、+$0.000461 USD（約1.24倍）増加した。

３ 考察
　今回の実験では、p.37（章扉）、p.41（Skill）、p.64（長時間タスク）、p.66（AGENTS.md・Skills）など質問と直接関係しない周辺ページも返され、不要なコンテキストが増加した。
　章扉などは何らかの方法であらかじめ混入しないような方法が望まれる。
　また、前後2ページ以上離れた関連ページや資料外の質問には対応できない点も改善の余地がある。
